= Enforcing Best Practices with Hypersistence Optimizer
Vlad Mihalcea
:source-language: java
:sourcedir: {examplesdir}

In this chapter, we are going to see how Hypersistence Optimizer turns the performance best practices
from this book into checks that run inside your build.

This book has spent hundreds of pages explaining which mappings are fast and which are slow,
but all this knowledge is only useful if it survives the next commit.
While having someone review your pull requests is a great idea,
it is not a guarantee that every regression will be caught, especially when so many layers are being abstracted away by Spring Boot.

So, a much better practice is to automate the checks, which ensure that your mappings and configurations are not only correct,
but also allow your application to perform as required by the Service Level Agreements (SLAs) of your business.

For instance, what if someone joins the team and adds a `@ManyToOne` annotation using the default `FetchType.EAGER`
because the IDE autocompleted it?
Or, what if someone leaves the https://stackoverflow.com/questions/30549489/what-is-this-spring-jpa-open-in-view-true-property-in-spring-boot[Open Session in View (OSIV)] mode enabled, which is a common source of N+1 problems?
Even if you know all these rules, that is not sufficient, since not everyone on the team may be aware of them,
and even if they are, they may forget to apply them, especially when there is a rush to deliver a new feature.

https://vladmihalcea.com/hypersistence-optimizer/[Hypersistence Optimizer] addresses this problem by scanning
your `EntityManagerFactory` and reporting each performance-related violation as an `Event` object.
Because it is an object and not just a log line, you can assert on it programmatically.
Therefore, a mapping regression can fail a build the same way a broken unit test does.

The scanner inspects three things, and we are going to take them one at a time:

* the **JPA entity mappings**,
* the **Hibernate configuration**, and
* the **runtime** behavior that no annotation review can catch, such as long-running queries or transactions.

In the end, we are going to turn all three into a quality gate that enforces the best practices from this book
in your build, so that you can be sure that your application will perform as expected.

[NOTE]
====
Hypersistence Optimizer is a commercial product and is not published to Maven Central,
so the projects in this chapter are **not built by default**.
They are contributed by Maven profiles that activate only when the artifact is present in your local repository.

If you don't have the library in your Maven repository, the rest of the test project builds normally.
If you do have the tool, just make sure that you are using the `jakarta`-classified artifact
because Spring Boot 4 uses Jakarta Persistence.

See `HibernateSpringBootOptimizer/README.md` for the details about how to build the testing module.
====

When this bean is constructed at runtime, it scans every JPA and Hibernate mapping,
as well as the entire Hibernate configuration that bootstraps the `EntityManagerFactory`.

The results are available through the `getEvents()` method, and each `Event` carries a priority (`BLOCKER`, `CRITICAL`, or `MAJOR`),
a description of what is wrong and why, and a link to the documentation that provides more details about the associated performance rule.

The rest of this chapter walks the same forum through the three kinds of events that the scan produces.

== Mapping issues

The first thing the Optimizer inspects is your entity mappings.
Almost everything this book has taught about associations and identifiers shows up here,
reported as an `Event` the moment you get the mapping wrong.

=== The forum, mapped badly

The first example project we are going to analyze is `HibernateSpringBootOptimizerKickoff`,
which you can find in the `HibernateSpringBootOptimizer` module of the book code repository.

Let's consider that we have the following `PostDetails` entity mapping in our code base,
which is not very different from many examples you are going to stumble upon in articles or on Stack Overflow:

At first glance, nothing in this mapping seems exotic or out of place.
However, there are two defects in these few lines of code.
First, the `PostDetails` row carries its own surrogate key instead of sharing the identifier
with the parent `Post` entity,
which costs an extra column, an extra sequence, and a unique index.
Second, `@OneToOne` defaults to the `EAGER` fetching strategy,
so loading the details entity will always load the associated post, whether or not we actually need it.

====
The examples run on PostgreSQL, where `@GeneratedValue` resolves to a sequence generator.

On MySQL, the same model reports four `TableGeneratorEvent`s as well,
because MySQL has no sequences, so `@GeneratedValue` has to fall back to a table generator.

The Optimizer recommends `IDENTITY` in that case, although `IDENTITY` disables JDBC batch inserts.
However, there is a way to enable batch inserts with `IDENTITY` on MySQL, but it requires a
very complex mapping that is beyond the scope of this chapter.
You can find a working example in this https://github.com/vladmihalcea/high-performance-java-persistence/blob/0f8f5a4361fb8323b6151010324811ea6408a0e0/core/src/test/java/com/vladmihalcea/hpjp/hibernate/batch/identity/stateless/MySQLIdentityStatelessSessionTest.java#L17[GitHub repository].

In the second project, `HibernateSpringBootOptimizerMappingFixes`, we will have all the previous mapping issues fixed,

----
include::{sourcedir}/HibernateSpringBootOptimizer/HibernateSpringBootOptimizerMappingFixes/src/main/java/com/bookstore/forum/entity/PostDetails.java[tag=mapsid,indent=0]
----

Each change clears a specific event:

* `FetchType.LAZY` on both associations clears the `EagerFetchingEvent`, once for each association.
* `@MapsId` on top of a bare `@Id Long id` clears the `OneToOneWithoutMapsIdEvent`,
  and the surrogate key goes away with it.
* `optional = false` on the parent side of the `@OneToOne` clears the `OneToOneParentSideEvent`.
  Only when Hibernate knows that the row must exist can it proxy the association,
  instead of running a query to find out whether it should store a `null`.
* `Set<Tag>` instead of `List<Tag>` clears the `ManyToManyListEvent`.
  Removing one tag now deletes a single join-table row,
  rather than deleting all of them and re-inserting the ones that survived.
* Adding the `addPostComment` and `removePostComment` methods clears the `BidirectionalSynchronizationEvent`.

== Configuration issues

After scanning the entity mappings, the Optimizer inspects Hibernate configuration, no matter if you provided it
declaratively, via the Spring `application.properties`, `application.yml`,
or programmatically using the `LocalContainerEntityManagerFactoryBean`.

For example, let's investigate the configuration-related events that the `HibernateSpringBootOptimizerKickoff` project reports.

=== Eight configuration defaults working against you

The other eight findings from that first scan come straight from the Hibernate configuration:

[cols="1,3", options="header"]
|===
| Event | What it costs you

| `SchemaGenerationEvent` (BLOCKER)
| `ddl-auto=create`. Hibernate auto-generates the database schema, so schema migrations are not versioned
  and we cannot use database-specific DDL.

| `JdbcBatchSizeEvent`
| The `hibernate.jdbc.batch_size` is not set, so JDBC batching is disabled.

| `JdbcBatchToBulkInsertEvent`
| On PostgreSQL, we should enable `reWriteBatchedInserts` so that a batch of inserts can be rewritten
  into a multi-value `INSERT`.

| `ConsoleStatementLoggingEvent`
| `show-sql=true` logs SQL statements through `System.out` instead of a proper logger framework.

| `SkipAutoCommitCheckEvent`
| Hibernate does not know if the connection pool had already disabled autocommit, so it must check the autocommit flag at the beginning of each transaction, which prevents lazy connection acquisitions.

| `QueryPaginationCollectionFetchingEvent`
| The data access layer can issue a collection `join fetch` on a paginated query, which leads to in-memory pagination, as opposed to SQL-level pagination.

| `QueryInClauseParameterPaddingEvent`
| By default, an `IN` clause needs to list all parameter placeholders in the SQL statement, which may cause unnecessary cache misses if statement caching is enabled.

| `DefaultQueryPlanCacheMaxSizeEvent`
| The default size of entity query plan cache is 2048 and many applications could benefit from a larger cache that will prevent JPQL, Criteria API, and Spring Data query methods from being parsed over and over.
|===

The advantage of using Hypersistence Optimizer is that you are going to be notified about new configurations that are added by Hibernate or JDBC Driver implementors.
So, you don't have to manually scan every release note from Hibernate, Spring Data JPA, or the JDBC Driver in search
of new performance-related settings that you may have missed, such as the `reWriteBatchedInserts` property of the PostgreSQL JDBC Driver,
which was added in the 9.4.1209 version (2016), yet few applications ever enable it.
When you upgrade the Hibernate version, either directly or via a Spring Boot version bump,
the Optimizer can detect if there are new settings worth configuring,
so you can make sure that you are always up to date with performance-related settings that, otherwise, are very easy to miss.

==== Connection-related settings

Disabling autocommit on the Hikari pool with `spring.datasource.hikari.auto-commit=false`
clears the `SkipAutoCommitCheckEvent` altogether.
While for a regular Spring application, you'd need to also set `hibernate.connection.provider_disables_autocommit=true`,
since that is the property Hibernate reads before deciding whether to check the autocommit status
at the start of every transaction, you don't need to do that in a Spring Boot application.

When Spring Boot builds the `EntityManagerFactory`, its `HibernateJpaConfiguration` inspects the connection pool
through the `DataSourcePoolMetadata`, and when the pool reports that autocommit is disabled,
Spring Boot sets `provider_disables_autocommit` to `true` on your behalf.

So, the `hikari.auto-commit` setting is enough, and the Optimizer sees the Hibernate property
that Spring Boot derived from it.

Another connection-related setting is `spring.jpa.open-in-view=false`, which disables the Open Session in View (OSIV)
anti-pattern that Spring Boot enables by default due to convenience, not because it is a good idea from a performance perspective.

==== Batching-related settings

Setting `hibernate.jdbc.batch_size` enables JDBC batching and clears the `JdbcBatchSizeEvent`,
while `order_inserts` and `order_updates` reorder the `INSERT` and `UPDATE` statements when flushing the `EntityManager`,
as otherwise, cascading could interleave statements and prevent batching.

On PostgreSQL, the `reWriteBatchedInserts` flag on the JDBC URL lets the driver rewrite
a batch of inserts into a single multi-value `INSERT`, which clears the `JdbcBatchToBulkInsertEvent`.

==== Schema-related settings

Setting `ddl-auto=none` hands schema management to a migration script instead of Hibernate,
which clears the `SchemaGenerationEvent`.

It's also fine to use `ddl-auto=validate`, which checks the database schema at startup in order to ensure
that it matches the entity mappings.
If you're using Flyway or Liquibase to manage your schema, you want to make sure that the DDL changes
you are making while developing a new feature are compatible with the entity mappings,
and `ddl-auto=validate` is how you can automate this check.

==== Logging-related settings

Routing SQL through a logger instead of `System.out` clears the `ConsoleStatementLoggingEvent`,
which is why there is no `show-sql=true` here.

The advantage of using a logging framework is that you can configure the logging level for SQL statements based on the
underlying environment, and you can also choose where the log messages are routed, such as a file, the console, or a remote logging server.

==== Query-related settings

The `fail_on_pagination_over_collection_fetch` property turns in-memory pagination over a fetched
collection into an error and clears the `QueryPaginationCollectionFetchingEvent`.

The `in_clause_parameter_padding` pads the `IN` clause parameters to the closest higher power of two.
With this setting in place, the `IN` clause can generate the following series of placeholders:
1, 2, 4, 8, 16, 32, 64, 128, 256 and so on.
If the `List` of parameter values you're providing to the `IN` clause is smaller than the next power of two,
Hibernate will repeat the last parameter until it reaches the next power of two.
This padding trick allows Hibernate to use fewer SQL statements, instead of generating a new SQL statement
for every different number of parameters in the `IN` clause, which would cause problems for databases that cache query plans,
such as Oracle and SQL Server, as well as for the JDBC prepared statement cache since every different SQL statement
would be a different entry in the cache.

Therefore, by enabling the `in_clause_parameter_padding`, we clear the `QueryInClauseParameterPaddingEvent`.

The last setting, `spring.jpa.properties.hibernate.query.plan_cache_max_size=4096`,
increases the size of the Hibernate entity query plan cache so that it can accommodate more queries.

This is especially useful for applications that have a large number of queries,
or if you are using Criteria API and vary the query structure based on the input coming from the user.
By providing a larger `plan_cache_max_size`, the Optimizer clears the `DefaultQueryPlanCacheMaxSizeEvent`.

=== The end goal: a test that fails on any event

The clean scan we have just proven is the end goal.
The `reportsNoIssuesAtAll` test asserts that the event list is empty,
so the moment anyone reintroduces a single issue, whether it is a mapping regression or a configuration one,
that assertion fails and the build fails.

This is how the performance knowledge from this book can evolve from mere knowledge that you acquire
to an automated check.
The same way a build fails because a unit or integration test detected a business logic violation,
the build should also fail whenever a mapping or configuration regression is detected.

However, not every application can reach an empty Optimizer event list.
Some issues are inherent to the database we are using and cannot be fixed until the underlying database adds a feature we are expecting.
The best example that illustrates this situation is the identifier strategy on MySQL.
Because MySQL has no sequences, the only reasonable identifier strategy is `IDENTITY`,
even if it prevents Hibernate from batching inserts.
Because Hypersistence Optimizer reports an `IdentityGeneratorEvent` for every entity that uses the `IDENTITY` strategy,
there is nothing we can do to remove this event, since, in the absence of sequences, the `TABLE` strategy is even worse than `IDENTITY`.

To see this in practice, the `HibernateSpringBootOptimizerMySQLIdentity` project maps the same forum application for MySQL,
with each identifier declared as `IDENTITY`:

one for `Post`, one for `PostComment`, and one for `Tag`,
while the `PostDetails` entity shares its identifier through `@MapsId`, so it has no generator of its own.

[source,java]
----

An `EventFilter` is a predicate that decides whether an event is kept,
and this one keeps everything except an `IdentityGeneratorEvent`.

Notice that it skips an entire event type, which is the opposite of what you should normally do.
When we enforce the checks in the build, later in this chapter,
we will skip an event for a single entity and attribute,
so that it hides exactly one reviewed decision and nothing else.

The `IDENTITY` case is the exception that proves the rule, because the constraint is database-driven.
Every entity has to use `IDENTITY` on MySQL, so there is no single attribute to name,
and skipping the whole category is as narrow as the decision behind it.

this test will fail, because the `IdentityGeneratorEvent`s will no longer be present,
so we will then know that we have to remove the filter.

Enforcing the checks in the build is the most powerful feature that Hypersistence Optimizer offers you,
and you can apply it to all three event types: mapping, configuration, and runtime.

[TIP]
====
This kind of automated enforcement matters more today than it did a few years ago.
AI coding agents can now generate far more changes than a team was ever able to write by hand,
and they do so non-deterministically, so the same prompt can produce a different mapping or configuration each time.
The more code that is generated this way, the easier it is for a well-known performance anti-pattern to slip back in,
simply because there is more of it than any team can carefully review.

A deterministic tool like Hypersistence Optimizer, or a linter in general,
is what brings that determinism back, since it applies the same rules to every change,
no matter whether a person or an agent wrote it.
So, when the volume of changes is higher than the team's capacity to review them,
a check that fails the build on a known issue becomes even more valuable than it used to be.
====
